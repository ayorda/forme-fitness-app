# FORME — поддръжка на маркерите след изтриване

Обхват: минималният частен документ, оставен от потока за изтриване във v0.9.0. **Няма автоматично изпълнение, scheduler, Cloud Function или активирана платена услуга.** Докато оператор не извърши почистване, UID/времето остават. Това ограничение е описано в [PRIVACY.md](./PRIVACY.md); приемането на процеса за срокове остава част от 3.3.

## Защо има маркер

Firebase ID token може да е валиден около един час след изтриването на Auth акаунта. Ако документът просто се изтрие, стара сесия би могла отново да създаде архив. Затова `users/{uid}/private/snapshot` остава с точно `format:2`, `state:deleting`, `deletedAt`. Правилата отказват връщане към format1 и всяко клиентско изтриване. Всеки повторен опит за изтриване на акаунта подновява timestamp-а преди новия опит за Auth deletion.

## Проверка и изпълнение

Само оператор с вече разрешен административен достъп може да използва `maintenance/purge-deletion-marker.cjs`. Инструментът е извън приложния bundle/Service Worker и не използва частен ключ в клиентския код. Използва OAuth входа на официалния Firebase CLI; не създава service account или нови права. Текущият проект е фиксиран в кода: `forme-fitness-83c13`.

1. Установи точния UID от собствената Firebase Console при обработката на изрично искане/завършено изтриване. Не публикувай UID, архив или OAuth данни. Не избирай активния акаунт на собственика за тест.
2. Използвай актуален официален `firebase-tools`, наличен Node runtime и съществуващия CLI вход. Задай `FORME_FIREBASE_TOOLS_ROOT` към абсолютната папка на инсталирания пакет; при управлявана конфигурация `XDG_CONFIG_HOME` трябва да сочи към същата частна папка, използвана за CLI входа.
3. Изпълни **само проверка** (замени `UID_FROM_CONSOLE` с точния разрешен UID):

```bash
node maintenance/purge-deletion-marker.cjs --uid UID_FROM_CONSOLE
```

4. Само след преглед на `{ "eligible": true, "deleted": false }` изпълни действителното почистване:

```bash
node maintenance/purge-deletion-marker.cjs --uid UID_FROM_CONSOLE --apply
```

Инструментът отказва при съществуващ Auth потребител, грешка/невалиден отговор от Auth, грешен UID/път/формат, архив вместо маркер, допълнителни полета или невалидно време. Изисква минимум **2 часа след по-късното от `deletedAt` и Firestore `updateTime`**. Това е долна граница за защита, не обещание за автоматично изтриване след два часа.

При `--apply` отново проверява липсата на Auth UID и изтрива само точния документ с Firestore `currentDocument.updateTime` precondition. Промяна между проверката и изтриването отказва операцията; няма повторен опит без нов преглед. Не се изтриват други документи, колекции или самата база. Успешното изпълнение връща `{ "eligible": true, "deleted": true }`, без съдържание или credentials в изхода.

При отказ спри и провери причината в разрешения административен интерфейс. Не отслабвай правилата, не отписвай грешка в заявката като „потребителят липсва“ и не изтривай ръчно свеж маркер. Маркер за неуспешно Auth deletion остава, докато потребителят повтори операцията или оператор обработи изричното му искане.

## Проверки и оставащи ограничения

- `privacy.test.js`: 8 теста за dry-run/apply, отказ за активен акаунт, отказ при Auth грешка, строг формат/път, минимум време, повторна Auth проверка и конфликт на версията. Тестовете използват изолирани функции, без production изтриване.
- `qa/firestore-rules.mjs` и реалният локален SDK сценарий проверяват, че стар токен не може да възстанови payload след маркера. Самият admin helper не е изпълняван разрушително върху реален потребител/маркер в production.
- Няма списъчно сканиране, cron, гарантиран срок/SLO или автоматична обработка на искания. Трябва да се приемат работен процес и крайни срокове и да се провери поддръжката с подходящ разрешен тестов запис преди широко използване. Не се активира платен TTL за тази задача.
